# AGENTS.md: NAVRelay implementation blueprint

Updated: 2026-08-25

## 1. Scope

NAVRelay handles Hungarian invoices from draft through final NAV result. It accepts structured data through the native API or authenticated admin UI, validates it, assigns a number from a server-managed invoice series (`számlatömb`), generates or completes the PDF through an approved render path, stores one immutable canonical document in S3-compatible storage, and reports it through the official NAV Online Számla interface.

```text
draft -> validate -> allocate number and lock snapshot -> render PDF
      -> validate and store exact canonical bytes -> ISSUED
      -> NAV submit and poll -> final NAV result
```

The admin UI and organization apps call the same application services and issuance API. Manual entry is an input method, not a second invoice engine.

PDF modes:

- `NAVRELAY_RENDERED`: the worker renders from the locked snapshot.
- `TRUSTED_CLIENT_RENDERED`: NAVRelay returns the server-assigned number and locked snapshot in a scoped package; an approved app returns PDF bytes only.

Every organization has isolated `TEST` and `PRODUCTION` environments. Data, numbering, credentials, storage, jobs, delivery, and NAV traffic never cross between them.

## 2. Authority and invariants

Resolve conflicts in this order:

1. Current Hungarian law and official NAV specifications.
2. This file.
3. Repository code and migrations.
4. Framework defaults and third-party examples.

Mandatory rules:

- Expose each business operation through the documented native autogenerated open API with its admin UI.
- Let authorized users create, edit, preview, and issue invoices manually in the admin UI.
- Allocate every final number on the server from an authorized NAVRelay-managed series. Callers never provide a series identifier, series configuration, sequence, numbering mode, or final number.
- Give every issued invoice one canonical PDF. Preserve its exact bytes and append-only metadata.
- Store canonical documents in private S3-compatible storage. PostgreSQL stores state, metadata, and object references, not production PDF blobs.
- Report directly through a pinned, versioned NAV adapter. A transaction ID is intermediate; continue until NAV returns a final result.
- Use exact decimals or integer minor units. Never use JavaScript floating point for money or tax.
- Correct, cancel, or reverse an issued invoice with a new linked legal document, never an in-place edit.
- Scope all operational state to an organization and environment. Derive both from authenticated server-side context.
- Make API calls, webhooks, jobs, retries, and restarts idempotent. They must not duplicate invoices, numbers, documents, or NAV submissions.
- Fail closed for unsupported tax cases, uncertain compliance, authorization errors, environment mismatches, invalid documents, and incomplete NAV mappings.

This is an engineering blueprint, not legal advice. Before production, obtain written Hungarian accounting or tax-law approval for supported invoice types, required fields and wording, VAT and exemptions, reverse charge and OSS, currencies and HUF VAT, advance/final/corrective/cancellation flows, electronic-invoice authenticity and `electronicInvoiceHash`, retention and statutory exports, renderer trust and timing, and provider-to-tax mappings.

NAV conformance is a release gate. Every supported case must match the pinned official interface and XSD, pass project fixtures and NAV test-environment checks, and appear in the approved scenario matrix. Never claim support for an untested case.

## 3. Stack and architecture

Use repository-pinned versions. Otherwise use:

- TypeScript, modern Node.js with native ESM, and pnpm pinned through `packageManager`;
- Nuxt, Vue Composition API, SSR, Nuxt UI, Tailwind CSS, Nuxt i18n, and `nuxt-open-fetch`;
- NestJS by business domain, `class-validator` on write DTOs, and generated Swagger/OpenAPI;
- PostgreSQL, MikroORM migrations, Better Auth sessions and Organization plugin;
- a durable worker, private S3-compatible storage, and email behind a backend abstraction;
- Vitest, Supertest, Testcontainers, and Playwright.

Preferred workspace:

```text
NAVRelay/
├─ apps/
│  ├─ web/                 # Nuxt admin and audit UI
│  ├─ api/                 # NestJS native API and webhooks
│  └─ worker/              # PDF, NAV, export, integrity, delivery jobs
├─ packages/
│  ├─ nav-online-invoice/  # NAV transport, XML, signing, parsing
│  ├─ invoice-domain/      # values, state rules, calculations
│  ├─ pdf-renderer/        # deterministic internal rendering
│  ├─ storage/             # S3 and integrity helpers
│  ├─ api-client/          # generated output only
│  └─ test-fixtures/       # official and project fixtures
├─ docs/{compliance,architecture,operations}/
├─ .github/workflows/{verify.yml,nav-contract.yml}
├─ defaultstack.md
├─ AGENTS.md
├─ pnpm-workspace.yaml
└─ package.json
```

```text
Organization user -> Nuxt admin -> NestJS native API
Organization app  -> public /v1/* -> NestJS native API
Provider webhook  -> narrow signed route -> NestJS native API
NestJS -> PostgreSQL for domain, job, and audit state
NestJS -> durable queue -> worker -> renderer, S3, NAV, delivery
Trusted renderer app -> scoped package -> PDF handback endpoint
```

NestJS owns authorization, validation, issuance, tenancy, environment selection, and idempotency. Workers perform retriable external work. PostgreSQL owns state and metadata; S3 owns canonical bytes. Share domain services between API and worker, but keep controllers, consumers, and adapters separate. Never duplicate tax, numbering, or lifecycle rules at entry points.

## 4. Organizations, users, apps, and authorization

```text
Organization
├─ Users through OrganizationMembership
├─ Apps
│  └─ AppCredentials, each bound to TEST or PRODUCTION
└─ Environments
   ├─ TEST
   └─ PRODUCTION
```

A user may join several organizations. An app belongs to exactly one organization and is a machine principal, never a fake user. An app may have separate test and production credentials; each credential is bound to one `OrganizationEnvironment` and cannot switch it. The app record alone never authorizes or selects an environment. Requests, renderer handbacks, webhook registrations, and jobs resolve through an environment-bound credential or integration.

Mirror Better Auth's `User`, `Session`, `Account`, `Verification`, `Organization`, membership/member, and invitation model exactly in MikroORM migrations. Better Auth owns runtime identity, sessions, organization membership, invitations, active organization, and member roles. MikroORM owns DDL and migration history; disable Better Auth production auto-migration. Define roles in typed Better Auth access-control code, not parallel role tables. Disable generic organization deletion; retained organizations enter a closed archival state.

NAVRelay owns at least `OrganizationEnvironment`, `EnvironmentGrant`, `App`, `AppCredential`, `NavConnection`, `InvoiceSeries`, `TaxProfile`, `Customer`, invoice and line entities, `InvoiceDocument`, `InvoiceRenderRequest`, `RendererProfile`, invoice relations, payment references, NAV submissions and messages, provider integrations and events, audit shares and events, exports, stored objects, and durable jobs or outbox rows.

Human roles:

- `owner`: organization, users, apps, credentials, environments, and all data.
- `admin`: users, apps, settings, series, tax profiles, NAV connections, and invoices.
- `accountant`: customers, invoices, NAV results, exports, corrections, and cancellations.
- `operator`: supported draft, preview, and issue operations.
- `auditor`: read-only invoice, document, NAV, audit, and export access.
- `viewer`: limited read access.

Membership never automatically grants both environments. `EnvironmentGrant` binds one organization membership to one environment and separates access from invoice-issue permission. Switching the active environment validates that grant and writes the context to the server-side session. A selector, cookie, header, URL, or request field is never authorization.

App credentials need a recognizable prefix, secret hash, environment, scopes, status, rate limits, creation and rotation data, last-used time, expiry, revocation, and audit metadata. Show plaintext once and never make it retrievable. Useful scopes include draft write, invoice issue, invoice read, renderer handback, and export read.

Every query and mutation must derive allowed organization and environment from the session or app credential, then scope all lookups and storage access. Never trust caller-supplied ownership fields. Authorize before issuing a presigned URL. Use repository and service methods that require tenant context.

Put `organizationId` and `environmentId` on operational rows directly or through an unavoidable parent. Use composite foreign keys or equivalent constraints so a child cannot reference a parent from another organization or environment. Cover invoices, documents, render requests, NAV submissions, provider events, exports, shares, stored objects, jobs, and outbox rows. Include both values in relevant uniqueness constraints.

## 5. Environments and test mode

`TEST` and `PRODUCTION` run the same invoice engine, validation, calculation, rendering, hashing, audit, storage, and NAV adapter. Test mode is isolation, not relaxed validation.

Each environment has separate NAV connections and credentials, series and counters, tax and renderer profiles, S3 bucket or strict immutable prefix, provider configuration and webhook secrets, source and idempotency records, jobs, audit data, shares, exports, and delivery configuration.

`TEST` rules:

- Use only `https://api-test.onlineszamla.nav.gov.hu/invoiceService/v3` or an explicit local NAV mock.
- Use test-only series and numbers.
- Mark the UI, responses, previews, PDFs, downloads, and exports `TEST` and `NON-PRODUCTION` with compliance-approved wording.
- Snapshot that marker requirement in the renderer profile. A trusted renderer must attest to it and pass validation; never stamp returned bytes afterward. If it cannot guarantee the marker, use `NAVRELAY_RENDERED` or reject the attempt.
- Send through a sink or a fixed allowlist of internal test addresses. Never use customer addresses or live delivery targets, regardless of delivery adapter.
- Keep test metrics, audit, reconciliation, and operational exports separate. Test data never enters production metrics, exports, delivery, retention reports, statutory filings, or reconciliation.
- Reject production statutory export formats for test data.

`PRODUCTION` uses only `https://api.onlineszamla.nav.gov.hu/invoiceService/v3`. It starts disabled for a new organization. An owner or admin may enable it only after the NAV connection, series, tax and renderer profiles, storage, retention, and delivery checks pass. The admin UI keeps the environment visible and requires explicit confirmation before production issue.

A `NavConnection` becomes immutably bound to one `OrganizationEnvironment` after first use. Endpoint or credential mismatches fail readiness and runtime checks. Startup and readiness validation covers NAV, providers, S3, email, and every delivery adapter. A test process fails readiness if any configured target or credential is production, and the reverse.

Every outbox payload carries organization and environment. Before each external call, workers recheck the environment-bound NAV, provider, storage, email, and delivery configuration. Any mismatch fails closed.

Register separate provider webhook endpoints or secrets for each environment. Resolve organization and environment from the verified endpoint and signature, never the event body. Verify any provider sandbox/live marker and use the same environment-bound credentials for worker fetches.

There is no promotion or cross-environment clone operation. Drafts, numbers, invoices, render attempts, PDFs, hashes, NAV results, provider IDs, idempotency records, and object keys remain in their source environment. Production always begins with a new production draft and allocation.

## 6. Native API and admin UI

Serve the documented native API at public HTTPS `/v1/*`, `/openapi.json`, and `/docs`. Authenticate app calls with scoped environment-bound credentials; rate-limit them and require idempotency for externally visible writes. Keep user-session, app, and webhook guards and DTOs separate while calling the same domain services. Never expose worker, queue, migration, or maintenance endpoints publicly.

Core inputs:

1. An authorized admin user creates, edits, validates, previews, and issues a draft.
2. An authenticated app performs the same operations through `/v1`.
3. A trusted renderer returns bytes only for a scoped server-created render attempt.
4. An optional verified provider event supplies payment, source, or tax evidence and triggers managed issuance.

The admin UI is a required manual invoicing client. It uses the same draft, preview, issue, PDF, storage, and NAV services as apps. It cannot access the database directly or implement separate issuance logic.

Baseline resources:

```text
/v1/organizations/{organizationId}/{users,invitations,apps}
/v1/apps/{appId}/credentials
/v1/organization-environments
/v1/nav-connections
/v1/invoice-series
/v1/tax-profiles
/v1/customers
/v1/invoice-drafts
/v1/invoice-drafts/{draftId}/{preview,issue}
/v1/invoices
/v1/invoices/{invoiceId}/{document,nav-submissions,relations,render-requests}
/v1/invoice-render-requests/{renderRequestId}
/v1/invoice-render-requests/{renderRequestId}/{document,finalize}
/v1/audit-shares
/v1/exports
/webhooks/{provider}/{environment-bound-route}
```

No endpoint accepts an issued invoice, external number, standalone final PDF, remote PDF URL, unrestricted S3 key, caller-controlled environment, raw series choice or configuration, sequence, numbering mode, final number, or NAV code. A draft preview never allocates and is visibly marked as a draft. Responses may expose the server-resolved environment and series snapshot as read-only data.

## 7. Invoice data, tax, and state

Number allocation locks a versioned invoice snapshot containing:

- organization, environment, supplier, customer, and their required tax identities;
- number, issue time, performance date, due date, and source principal;
- currency, exchange-rate facts, payment method, and payment reference;
- lines, quantities, units, discounts, adjustments, exact net/tax/gross totals;
- tax categories, legal reason codes, language, notes, and required wording;
- original, correction, cancellation, advance, and final relations;
- source system and source identifiers.

Hash the deterministic serialization with SHA-256 and bind render attempts to its schema version and hash. Keep mutable business, document, NAV, and delivery states plus document metadata outside the snapshot; append state history and lock document metadata at canonicalization.

State fields:

- Business: `DRAFT`, `ISSUING`, `ISSUED`, `CORRECTED`, `CANCELLED`.
- Document: `MISSING`, `GENERATING`, `AWAITING_CLIENT_PDF`, `STAGED`, `CANONICAL`, `FAILED`.
- NAV: `NOT_REQUIRED`, `PENDING`, `SUBMITTING`, `PROCESSING`, `ACCEPTED`, `ACCEPTED_WITH_WARNINGS`, `REJECTED`, `RETRY_REQUIRED`, `MANUAL_REVIEW`.
- Delivery: `NOT_REQUESTED`, `QUEUED`, `SENT`, `FAILED`.
- Operations: `NONE`, `RENDER_RETRY_REQUIRED`, `MANUAL_REVIEW`.

Every invoice uses an explicit, versioned, organization- and environment-approved `TaxProfile`. Callers provide its ID and facts. The profile defines VAT status and jurisdiction, rate or exemption, evidence, wording, rounding, currencies and exchange rates, and NAV mapping. Store profile and mapping versions, input facts, result, and any external calculation ID. External calculators provide evidence only; NAVRelay validates it and owns totals, the snapshot, and NAV mapping. Add supported tax cases one at a time and reject ambiguous facts.

## 8. Numbering and issue transaction

Invoice series are always NAVRelay-managed and environment-scoped. Drafts have no number. The caller selects an enabled issuance profile; server policy resolves the authorized series. Store its organization, environment, name, public format, counter, reset policy, allowed document and renderer modes, optional currency limits, active state, first and last issue times, configuration versions, and audit data.

Allocate only in the transaction that creates the locked `ISSUING` invoice:

```text
begin
  lock and validate organization, environment, issuance profile, and series
  allocate next sequence
  persist unique final number and immutable invoice and series snapshots
  create render job or scoped render attempt and durable outbox row
  increment series counter and append audit event
commit
```

Use a row lock, atomic update, or equivalent PostgreSQL serialization. Do not render, upload to S3, call NAV, send delivery, or make any external call inside this transaction.

Allocation is irreversible. A timeout, invalid PDF, worker crash, or NAV failure cannot release or reuse the number. Keep sequence gaps visible and retry only against the same number and snapshot. After first use, never change a series format, reduce its counter, reuse a number, or delete the series; deactivate it and retain its history.

## 9. PDF rendering and canonicalization

Each allocated invoice can produce one canonical `InvoiceDocument`; every `ISSUED` invoice has exactly one. Both render modes validate the draft and profiles, allocate and lock snapshots, render or receive bytes, validate and hash the exact PDF, store it unchanged at a new canonical key, then atomically set document `CANONICAL` and business `ISSUED`. NAV becomes runnable only after canonical bytes and required hashes exist. Delivery queues only after canonicalization.

For `NAVRELAY_RENDERED`, the worker renders only from the snapshots. Record renderer and template versions, locale, fonts, and assets. Rendering must be reproducible for investigation and must never replace a canonical object. Admin-created invoices use this mode by default.

For `TRUSTED_CLIENT_RENDERED`, require an enabled `RendererProfile` and a scoped renderer app. Allocation creates an `InvoiceRenderRequest`. Return invoice and attempt IDs, server number, immutable series snapshot/version, invoice snapshot/version/hash, approved renderer and template metadata, expiry, and a short-lived attempt token or staging target. Show the token once, store only its hash, and never log it. Bind it to organization, environment, invoice, attempt, snapshot, renderer, content type, maximum size, and staging key.

```text
POST /v1/invoice-drafts/{draftId}/issue
  -> ISSUING, final server number, locked render package, attempt token

PUT /v1/invoice-render-requests/{id}/document
  -> validate and finalize exact bytes, or record a staged upload

POST /v1/invoice-render-requests/{id}/finalize
  -> verify staged object -> promote unchanged bytes -> CANONICAL/ISSUED
  -> NAV outbox and delivery

POST /v1/invoices/{invoiceId}/render-requests
  -> replacement attempt for the same number and snapshot
```

The client may render only the package. It cannot change the series, number, dates, tax, totals, wording, or NAV codes. Returned bytes are renderer output for a NAVRelay-issued invoice, not an imported legal document. Store them without rewriting, optimizing, linearizing, stamping, metadata edits, or re-rendering.

Attempts use `ACTIVE`, `FINALIZING`, `SUPERSEDED`, `EXPIRED`, `FAILED`, or `CANONICAL`. An active attempt accepts repeated identical bytes with the same token until expiry. After canonicalization, an identical retry with a still-valid token returns the existing result without writing; conflicting bytes fail. A replacement keeps the number, snapshots, and renderer-profile version, issues a new token, and atomically supersedes the old active attempt. Never supersede `FINALIZING`. A database guard permits only the current attempt to canonicalize. Reject late callbacks from expired, failed, or superseded attempts.

Status lookup and replacement-attempt creation recover lost responses and expired tokens without allocating again. Every attempt has a bounded policy deadline. Before that deadline, a failed handback sets `RENDER_RETRY_REQUIRED`. At expiry, set the attempt `EXPIRED` or `FAILED`, keep the invoice `ISSUING`, set operations `MANUAL_REVIEW`, alert operators, and block NAV and delivery. It never waits silently, returns to editable `DRAFT`, or releases its number. Keep the snapshot, number, incident, and attempts in lists, sequence reports, exports, audit, and retention.

The renderer's authenticated handback attests to the bound snapshot; generic PDF parsing cannot prove complete semantic equality. `RendererProfile` snapshots approved identities, template versions, disclosure scope, deadline, attestation, and validation rules. Use internal rendering or reject issuance when policy needs stronger verification.

Validation checks PDF magic, actual content type, size, encryption/password policy, malware scan for public uploads, active attempt scope, renderer identity, and profile version. Optional text extraction may reject obvious number, supplier, or total mismatches, but the snapshot remains authoritative and OCR never is. Previews are separate objects.

If NAV needs `electronicInvoiceHash` derived from the PDF, handback and submission must meet the approved timing. Disable client rendering for profiles that cannot. Allocation may create a non-runnable `NavSubmission` intent in `PENDING`; only the canonicalization transaction inserts the runnable NAV outbox row.

## 10. Storage, hashes, and retention

Keep buckets private and separate environments by bucket or strict prefix plus credentials. Use server-side encryption, avoid personal data in keys, enable versioning where possible, and prefer Object Lock or an approved equivalent. If a provider cannot meet immutability needs, change it or document an approved compensating control. Back up or replicate objects under the approved disaster-recovery policy. Never fall back to app disks or Railway volumes. Canonical metadata lives in PostgreSQL; never overwrite a canonical key. Lifecycle rules apply only to staging, previews, failed uploads, and temporary exports.

Store SHA-256 and algorithm, byte length, MIME type, object key, S3 version ID, upload and finalization times, and any NAV electronic-invoice hash and algorithm. An S3 ETag is not an integrity hash. The versioned NAV adapter derives `electronicInvoiceHash` according to the pinned schema, completeness indicator, archival method, official documentation, and test vectors. Periodically read object bytes and verify integrity.

```text
organizations/{organizationId}/environments/{environmentId}/
  invoices/{year}/{seriesId}/{invoiceId}/
    canonical/invoice.pdf
    nav/submission-{attemptId}-{request,response,result}.xml
    metadata/invoice-snapshot.json
  exports/{exportId}/export.zip
  audit-manifests/{manifestId}.json
```

Use opaque internal IDs. Authorize short-lived presigned URLs. Bind uploads to organization, environment, invoice, snapshot hash/version, attempt, renderer, type, size, token, and staging key. Finalization verifies the staged object and promotes the exact bytes to a new canonical key. Bind downloads to one authorized object; never store presigned URLs or expose permanent public links.

Store `retentionUntil` and policy version on production invoices and objects. Production follows the approved Hungarian policy; the initial target is at least eight years and may be longer. UI/API calls cannot shorten it. Legal holds override deletion. Closing an organization archives retained records instead of deleting them. Test data uses a separate policy and never satisfies production retention. Audit every allowed deletion and fail closed when policy is uncertain.

## 11. NAV Online Számla

Implement a versioned NAV adapter, initially v3:

```text
Test frontend: https://onlineszamla-test.nav.gov.hu/
Test API:      https://api-test.onlineszamla.nav.gov.hu/invoiceService/v3
Production:    https://api.onlineszamla.nav.gov.hu/invoiceService/v3
```

Never select an endpoint from request data. Each organization environment has its own technical user and `NavConnection`, credentials, submissions, and results.

The adapter owns namespaces, vendored or controlled XSDs, XSD validation, password hashing, signing and request IDs, token exchange, `manageInvoice`, stable retry identity, transaction-status polling, response parsing, normalized messages, endpoint selection, and credential separation. Controllers and domain or provider services must not duplicate NAV transport rules.

Required flow:

```text
ISSUED plus canonical document and required hashes
  -> durable NAV job
  -> build and XSD-validate exact request
  -> exchange token
  -> manageInvoice with stable logical operation identity
  -> store request, response, transaction ID, and timestamps
  -> poll durably
  -> parse technical and business messages
  -> ACCEPTED | ACCEPTED_WITH_WARNINGS | REJECTED | MANUAL_REVIEW
```

Support approved correction, cancellation, and technical-annulment operations, optional taxpayer lookup, and schema/capability reporting. Encrypt NAV credentials through a key-management abstraction, decrypt only where needed, keep test and production credentials separate, rotate without changing history, and never log passwords, keys, signatures, or authorization material. A connection test must not issue an invoice.

Retry timeouts, connection resets, temporary NAV failures, and safe status queries with bounded backoff. Do not blindly retry permanent validation errors. Preserve one logical submission and record attempts, next retry, last error code, and normalized category. Operators may retry after configuration fixes without changing the invoice.

Retain the pinned schema and adapter versions, mapping-policy version, normalized snapshot, exact outbound/response/result XML, logical and NAV transaction IDs, final status, messages, correlation IDs, timestamps, and attempt records. Exclude credentials and credential-derived fields from shares.

Treat official schemas and interface documents as executable contracts. Pin schema versions and checksums, XSD-validate outbound XML, use official examples and golden fixtures, keep typed versioned tax mappings, and isolate transport DTOs from the invoice model. A schema update requires mapping review, migration analysis, regression tests, test-environment contract checks, and release notes.

Maintain an approved supported-scenario matrix covering relevant VAT statuses and jurisdictions, taxable/exempt/out-of-scope/reverse-charge/OSS cases, currency and exchange rates, advance/final invoices, corrections and cancellations, required PDF wording, rounding, electronic hashes, archival, and statutory exports. Add one case at a time with official evidence, domain tests, real NAV test-environment checks, and compliance approval.

## 12. Corrections and relations

Issued invoices are immutable. Model original, corrective/modifying, cancellation/storno, advance-to-final, and approved replacement relations. Each legal document gets a new managed number, locked snapshot, canonical PDF, NAV submission, and explicit link. Relations cannot cross organization or environment. Preserve the full chain in the API, UI, audit, and exports.

## 13. API contract and idempotency

NestJS controllers and typed DTOs define OpenAPI. Use JSON except explicit uploads/downloads; publish examples, error schemas, machine codes, localized messages, correlation IDs, versioning, and deprecation policy. Use cursor pagination and stable filters for environment, date, series, number, customer, source, business/document/NAV state. Do not accept `any` request bodies or return raw entities.

Require `Idempotency-Key` for issue, correction, cancellation, share, export, and provider-triggered writes. Store organization, environment, user/app principal, method and normalized route, key, request hash, state/result, safe response code and body, creation time, and expiry. The same hash returns the original result; a changed hash conflicts.

Do not persist plaintext render tokens in idempotency records. If the issue response and token are lost, create a replacement render attempt for the same locked invoice.

Enforce unique keys for `(organization, environment, invoiceNumber)`, logical NAV submissions, provider events, and source transactions. Provider identifiers are source and deduplication references only, never invoice numbers. Test identifiers cannot replay or deduplicate production work.

Generate the Nuxt client from OpenAPI with `nuxt-open-fetch`; keep generated files separate and unedited. Make `pnpm run verify` detect API and client drift. Publish a standalone SDK only after the API stabilizes.

## 14. Optional provider inputs

A verified provider event may supply payment/source facts or tax evidence and trigger the same managed issuance service. It never owns the series, number, snapshot, NAV mapping, or canonical PDF. Reject provider receipts and invoice PDFs as invoice documents.

Verify signatures on raw bodies, persist and deduplicate before acknowledgement, and fetch authoritative data in the worker with environment-bound credentials, allowlisted hosts, size limits, and content-type limits. Duplicate or reordered events must converge on one invoice. Refunds, voids, disputes, and credit notes enter explicit reconciliation or correction review; never map them automatically to Hungarian legal documents.

## 15. Jobs and transaction boundaries

Use a durable queue with safe multi-worker claims, retries, scheduling, and dead-letter or manual-review states. Required work includes internal rendering; trusted render dispatch, expiry, handback validation, and canonicalization; NAV submission and polling; delivery; exports; integrity checks; staging/export expiry; provider sync; and stuck-workflow reconciliation. The API may enqueue work but never rely on an in-memory queue.

Commit a domain change and its job/outbox row in one PostgreSQL transaction. This covers number allocation plus rendering work, provider event receipt plus processing, canonical metadata plus NAV work, and final NAV result plus notifications. A crash after commit must not lose work; a retry must not repeat the domain action.

No transaction spans PostgreSQL, S3, or NAV. For either render mode, render or receive outside the database transaction, validate and hash the exact bytes, then write a new canonical S3 object. A staged client upload must be verified and promoted unchanged. Only afterward may one PostgreSQL transaction lock the invoice and current attempt, record canonical metadata, set `ISSUED`, and insert the runnable NAV outbox row. NAV calls happen later. Reconciliation handles orphaned objects or interrupted finalization without replacing bytes or submitting early.

## 16. Audit, access, export, delivery, and security

Keep an append-only `AuditEvent` with organization, environment when applicable, actor type/ID, action, resource type/ID, time, request/correlation ID, safe user agent, redacted before/after configuration, outcome, and reason/source. Log successful and failed login; membership and role changes; app credential creation/rotation/revocation; environment and NAV configuration; invoice lifecycle and rejected edits; render attempts, handbacks, canonicalization, integrity checks, and downloads; NAV attempts/results; share creation/access/expiry/revocation; export creation/download; retention; and deletion. Application logs do not replace the audit log.

Authorized auditors may filter by date, invoice number, series, source, customer, business state, and NAV state; view canonical documents and safe NAV results; follow relations; verify hashes; and download allowed exports. They cannot alter invoices, series, NAV credentials, or documents.

Accountless `AuditShare` links use high-entropy tokens shown once and stored only as hashes. Bind each to organization, environment, immutable filters, allowed fields/actions, expiry, optional password hash and download limit, revocation, first/last access, and access log. Rate-limit attempts, use `noindex` and restrictive referrer policy, authorize each short-lived object URL, and never expose credentials, secret NAV payload fields, or unscoped organization data. Shares do not replace statutory exports.

Exports are asynchronous immutable snapshots. Support the approved Hungarian statutory format, selected PDFs with safe metadata, and explicitly implemented accounting formats. One export covers one environment; reject mixed filters and test requests for production statutory filing formats. Its manifest records filter snapshot, creator/share, invoice IDs and numbers, hashes and sizes, app and format versions, organization, environment, and creation time. Temporary export objects expire on a configurable schedule; source documents do not.

Delivery is not archival storage. Send the existing canonical PDF or authorized download link through an abstraction, localize messages, record attempts/provider IDs, and retry without regenerating the PDF.

Treat invoice data as sensitive. Use TLS, encryption for secrets, private least-privilege S3, hashed app/share/render tokens, input validation, webhook verification, provider-host allowlists plus fetch size and content-type limits, malware scanning, reauthorization on download, CSRF and login protection, and endpoint rate limits. Redact authorization headers/cookies, secrets, signatures, invoice bodies, customer PII, and PDF bytes from logs. Browser totals, roles, ownership, environment, and tax values are untrusted. Document hosted data-processing roles and support data-subject requests without breaking retention.

## 17. Frontend, persistence, and operations

The Nuxt admin UI includes organization and environment switching, persistent test/production labels, production confirmation, manual draft/preview/issue/correct/cancel flows, invoice/PDF/NAV detail, users and invitations, apps and credentials, customers, series, tax and renderer profiles, NAV connections, audit, shares, exports, retention, integrity, delivery, and alerts. Start with English and Hungarian, using English fallback. The UI uses the generated API client and duplicates no authorization, tax, numbering, or issue rules.

Use MikroORM's Unit of Work and PostgreSQL transactions. Generate migrations for every schema change and disable production schema synchronization. Restrict raw SQL or QueryBuilder to documented concurrency needs. Map entities to public DTOs.

Run Nuxt, API, PostgreSQL, and worker as separate Railway services using private networking. Apply migrations to non-production through a controlled release step, not on every start. Production migrations remain outside agent authority. Use bounded connection retries/pools, readiness checks that do not query the database per probe, and server-managed secrets. Keep test and production secrets separate. The same core may be self-hosted, but S3 remains mandatory; never fall back to local durable storage.

Use structured production logs with service, environment, correlation ID, safe organization/resource/job IDs, safe NAV transaction ID, outcome, duration, attempt, and next retry. Alert on stuck `ISSUING`, failed or expired renders, missing documents, NAV rejection/stalls, credential expiry, delivery failure, S3 integrity errors, dead letters, sequence conflicts, and abnormal idempotency conflicts.

## 18. Testing and verification

Prefer behavior and integration tests. Mandatory coverage:

- Better Auth organization creation, invitation acceptance, multi-organization switching, scoped roles and environment grants, and retained-data deletion blocks.
- Organizations own users through membership and apps directly. Valid scoped app credentials work; invalid, expired, revoked, wrong-environment, or under-scoped credentials fail. Machine writes enforce rate limits, idempotency, and tenant isolation.
- Admin and app issuance call the same validation, allocation, rendering, storage, and NAV services. Draft edits and previews allocate no number. Production issue requires active production context and explicit UI confirmation.
- Test and production series, counters, credentials, endpoints, objects, jobs, provider data, idempotency, exports, shares, metrics, and delivery cannot cross. Test records cannot clone or promote; readiness rejects endpoint/credential mismatch.
- Concurrent allocation is unique. Callers cannot provide environment, series, sequence, mode, or number. Failed rendering and restarts leave gaps visible and never reuse numbers.
- Render packages carry the server number, environment, and immutable invoice/series snapshots. Attempt tokens are shown once, hashed, unlogged, retry-safe, scoped, and expiring.
- Identical handback retries return the original result; conflicting bytes fail. Replacement attempts atomically supersede the old active attempt without another number. Expired, failed, superseded, late, cross-tenant, and cross-environment callbacks fail; only one attempt finalizes.
- Invalid, encrypted, oversized, or mismatched PDFs fail closed. Exact generated or returned bytes determine stored SHA-256 and NAV hash and remain unchanged. Test markers and renderer identity/profile/attestation are enforced.
- Presigned staging cannot canonicalize before explicit verification/finalization. S3 failure leaves recoverable state, not false issuance or delivery. Canonical metadata, `ISSUED`, and NAV outbox commit atomically after S3 canonicalization; NAV cannot run before bytes and hashes exist.
- NAV transient errors retry durably; permanent errors reach review without duplicate issue; transaction ID alone is not accepted. Official XML/XSD fixtures pass, and opt-in contract tests reach only the official test endpoint with test credentials.
- Provider signature, duplicate, ordering, environment, and source-deduplication cases fail safely or converge on one managed invoice. Provider PDFs remain rejected.
- Cross-tenant reads/writes/object access fail; canonical data cannot be edited; corrections preserve relations; share scope, password, expiry, and revocation work; export manifests match included files and hashes; retention blocks deletion; and logs are redacted.
- OpenAPI and generated clients include admin draft, preview, and issue operations, expose only the native API, and contain no external numbering or final-document import path.

Use Vitest, Supertest and `@nestjs/testing`, Testcontainers PostgreSQL, a real S3-compatible test service, official NAV XML/XSD fixtures, adapter-boundary mocks, opt-in NAV test-environment contracts, and Playwright on Chromium, Firefox, and WebKit.

The root `pnpm run verify` must cover formatting/lint, types, unit and integration tests, allocation/idempotency concurrency, PostgreSQL/S3 integration, OpenAPI drift, locale completeness, builds, and E2E. Claim full verification only when it passes; list skipped or blocked suites.

GitHub Actions must run the unchanged command under the stable check name `verify` for pull requests, protected-branch pushes, and `merge_group` when used. Pin Node and pnpm, use a frozen lockfile, read-only permissions, Linux/Docker/Testcontainers, and no organization or production secrets. Mock NAV, providers, email, and S3 at adapter boundaries in PRs. Run real NAV test-environment checks only in trusted manual/scheduled workflows with test credentials. Require `verify` before merge or automatic deployment of the same commit SHA.

## 19. Initial delivery and definition of done

Build in this order:

1. Organizations, memberships, invitations, roles, apps, environment-bound credentials, and environment grants.
2. Isolated test/production configuration and readiness checks.
3. Manual admin and native API draft, validation, preview, issue, list, detail, correction, cancellation, and PDF download.
4. Managed series and atomic allocation.
5. Internal rendering, then scoped trusted-renderer handback.
6. Private canonical storage, exact hashes, integrity checks, and retention.
7. Per-environment NAV validation, submission, durable polling, and final result.
8. Audit, scoped shares, manifest-backed exports, English/Hungarian text, and the verification gate.

An issuance feature is done when authorization and environment scope, typed validation, exact totals, idempotent allocation, locked snapshots, canonical PDF and hashes, NAV work and visible final state, audit, admin/API parity, test isolation, OpenAPI, generated client, targeted tests, and full `pnpm run verify` all pass. It is not production-ready until legal/compliance approval and real test invoices pass in NAV's test environment.

## 20. Forbidden scope and shortcuts

Do not:

- add another public invoice API or a second invoice engine;
- add general-ledger accounting, payroll, inventory, warehouse management, or unsupported tax regimes without a scope change;
- accept external series or numbers, provider-assigned numbers, issued-invoice imports, standalone final PDFs, provider PDFs/receipts, remote PDF URLs, or unrestricted object keys;
- allocate outside the issue transaction, reuse numbers, hide gaps, edit issued snapshots, or overwrite canonical objects;
- store canonical PDFs in database blobs, provider storage, local disk, or Railway volumes;
- let the UI bypass the native API, trust browser authorization or totals, or infer tax rules;
- mark NAV successful at transaction ID, call or poll NAV in a web request, or submit before canonical bytes and required hashes exist;
- expose public buckets or permanent object URLs, use ETags as hashes, or log secrets, raw invoice bodies, customer PII, or PDF bytes;
- select environment from request data, copy test data into production, or let test configuration reach live systems;
- silently change schema or mapping versions, delete retained documents, weaken `verify`, or expose control endpoints publicly.

## 21. Agent workflow and production safety

Never deploy, redeploy, promote, restart, roll back, or otherwise mutate production unless the user explicitly requests and confirms that exact action. Never use Railway CLI, API, MCP, or another deployment tool to change production or upload a local tree to production. Production migrations, database writes, environment-variable changes, service configuration changes, credential changes, and destructive operations are forbidden. Requested production inspection is read-only and limited to status, logs, and metrics.

Before changing code:

1. Read this file and `defaultstack.md`.
2. Map affected invariants, tenant/environment boundaries, document state, NAV mapping, and retention.
3. Check current official NAV specifications and any relevant provider contract.
4. Add generated MikroORM migrations for schema changes.
5. Test success, duplicates, concurrency, authorization, environment mismatch, retries, and failure recovery.
6. Regenerate OpenAPI and clients after API changes.
7. Run targeted tests, then unchanged `pnpm run verify`.
8. Report legal assumptions, missing specifications, unverified behavior, and blocked tests.

When uncertain, fail closed. Do not issue, expose, overwrite, promote, or delete a legal document on a guess.
